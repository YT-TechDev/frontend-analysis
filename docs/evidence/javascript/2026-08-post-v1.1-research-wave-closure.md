# JavaScript / ECMAScript Post-v1.1 Research Wave Closure

Status date: 2026-08-14

Classification: task and evidence record; non-normative.

## Purpose and Status

This record preserves the completed adversarial JavaScript / ECMAScript research
wave performed after acceptance of JavaScript Architecture Model v1.1.

It is supporting research evidence. It does **not** amend or override:

- [JavaScript / ECMAScript Architecture](../../architecture/JAVASCRIPT_ARCHITECTURE.md);
- [ADR 0009 — Define JavaScript Semantic Analysis Architecture](../../decisions/0009-javascript-semantic-analysis-architecture.md);

- [ADR 0008 — Define Browser Runtime Evidence Normalization and Core Import Ownership](../../decisions/0008-browser-runtime-evidence-normalization-and-core-import.md).

Architecture Model v1.1 remains accepted. This research wave found no
architecture-breaking contradiction and does not require an architecture revision.
Representation remains intentionally **OPEN**.

Repository work item: [#190 — freeze the post-v1.1 JavaScript research wave evidence](https://github.com/YT-TechDev/frontend-analysis/issues/190).

```text
ECMA-262, 17th edition, June 2026
```

Post-2026 drafts, ES2027 material, and proposals are not silently treated as

## Evidence Classification

This record preserves the evidence-layer distinctions used by the earlier
JavaScript research record:

- **N — Normative ECMAScript evidence**;
- **H — Normative host/Web evidence**;
- **T — Program-analysis / Abstract Interpretation theory**;
- **J — JavaScript-analysis empirical or published-system evidence**; and
- **A — Frontend Analysis architecture inference**.

The compact `A != B` statements below are durable evidence syntheses. They are
not presented as verbatim ECMA-262 propositions and do not prescribe a physical
representation. Where a statement crosses ECMAScript and host lifecycle
boundaries, the unresolved composition remains explicitly qualified rather than
being invented by the Core.

## Research Method

The post-v1.1 work continued the established architecture-first evidence method:

1. state a candidate semantic claim;
2. try to falsify it;
3. verify surviving claims against ECMA-262 2026;
4. construct theoretical counterexamples;
5. use runtime or engine evidence only when materially useful and keep it
   observational;
6. compare claims across prior evidence batches;
7. reject overly strong formulations;
8. distinguish normative fact, host/runtime behavior, empirical observation,
   architecture inference, and implementation possibility; and
9. keep implementation representation open unless evidence actually requires a
   commitment.

The durable interpretation rule remains:

```text
specification mechanism
!= implementation representation
!= observable semantic identity
```

## Durable Cross-Cutting Evidence

The following distinctions survived the final BA–BD contradiction audit. They
are semantic evidence constraints, not mandates for separate physical data
structures, Rust types, graphs, stores, crates, passes, or public APIs.

### Shared memory, atomicity, ordering, and provenance

```text
Shared-memory access
!= Atomic access
!= Synchronization
!= Happens-before
!= Reads-from
!= Value provenance
```

Atomic shared-memory operations have ordering guarantees, but an atomic
operation is not a universal synchronization edge, universal fence, or proof of
whole-program sequential consistency.

A value observation and the provenance of the write from which bytes are read
remain different information. Equal observed values do not establish equal
`reads-from` identity.

### Agent identity and execution concepts

```text
Agent
!= Thread
!= Realm
!= Job
!= Execution context

Agent identity
!= Agent liveness
!= Agent runnability
!= Agent progress
```

An Agent signifier identifies an Agent in specification state; it is not by
itself proof that the Agent is currently live, runnable, scheduled, or making
forward progress.

Agent-cluster membership is likewise not proof that every pair of Agents is
simultaneously alive or directly reaches one particular shared backing store.

### Waiting, notification, wakeup, and Promise delivery

```text
Wait registration
!= Suspension
!= Notification
!= Wakeup
!= Promise resolution
!= Promise reaction execution
```

`Atomics.notify` does not have one universal semantic effect for every waiter.
Blocking waits, same-Agent async waits, and cross-Agent async waits take
different specification paths.

For a cross-Agent async waiter, notification may lead to target-Agent Job
delivery before the associated Promise resolve operation is invoked. Promise
resolution remains distinct from later reaction execution and from execution of
user callback code.

Therefore:

```text
Notification performed
!= target Promise resolved

Resolve Job scheduled
!= target Promise resolved

Promise resolved
!= Promise reaction executed
```

### Synchronization state and payload state

```text
Synchronization fact
!= Payload-state fact

Notification
!= Predicate satisfaction
```

A synchronization relation or waiter notification does not imply that an
application-level shared-memory predicate became true. Synchronization metadata,
shared payload state, and observation of that state must remain distinguishable.

### Selection order, scheduling, fairness, and progress

```text
Waiter selection order
!= Critical-section acquisition order
!= Agent scheduling order
!= Callback execution order
!= Global fairness

Forward progress
!= Per-Agent global fairness
!= Application progress
```

FIFO waiter selection does not justify a global scheduling-fairness claim.
ECMA-262 contains scoped progress and liveness requirements, but those must not
be generalized into an unconditional guarantee that every Agent receives global
fair execution or that specification-level forward progress means useful
application-level progress.

### Job scheduling and execution

```text
Job scheduling
!= Immediate execution
!= Unconditional execution across arbitrary termination
```

A scheduled Job is governed by normative invocation rules when the relevant Job
invocation preconditions are reached. That is stronger than treating scheduling
as a purely best-effort hint.

However, this must not be strengthened into a universal claim that a Job will be
executed regardless of later externally permitted Agent termination. Job
scheduling semantics and Agent termination semantics are distinct contracts, and
the post-v1.1 audit found no universal ECMA-262 algorithm that reduces their
composition to one mandatory `execute`, `cancel`, `transfer`, or `reject`
outcome.

### Termination and pending operation cleanup

```text
Termination
!= Universal pending-operation cleanup
```

Agent termination does not by itself establish one universal cleanup rule for
pending Waiter Records, `waitAsync` Promise capabilities, or previously
scheduled Jobs.

The opposite universal claim is also unsupported: the evidence does not justify
saying that all such records necessarily persist forever.

The durable boundary is therefore that termination and pending-operation
lifecycle must not be silently conflated.

### State, observation, and causality

```text
State fact
!= Observation fact
!= Causal provenance fact
```

A fact about semantic state, a runtime observation, and evidence identifying the
cause or provenance of that state may be related without being interchangeable.
This remains especially important for shared-memory `reads-from`, asynchronous
Job delivery, notification, Promise settlement, and later callback execution.

## Strong Claims Rejected or Qualified

Future research, architecture, and implementation work must not silently
reintroduce the following stronger statements as assumptions.

### Rejected — atomic operation as universal fence

```text
Atomic operation
= universal fence
= universal synchronization edge
= whole-program sequential consistency
```

This is too strong. Atomic access semantics and broader program-ordering
properties must remain separately qualified.

### Rejected — AgentCluster as universal direct memory reachability

```text
Same AgentCluster
→ every pair directly reaches the same particular shared memory
```

Agent-cluster membership does not establish one specific directly reachable
shared backing store for every Agent pair or simultaneous liveness of every
member.

### Rejected — FIFO waiter selection as scheduling fairness

```text
FIFO waiter selection
→ FIFO Agent execution
→ global scheduling fairness
```

Selection, critical-section acquisition, Agent execution, callback execution,
and fairness are different relations.

### Rejected — universal per-Agent fairness

```text
Every unblocked Agent is globally guaranteed fair execution
```

This overstates the scoped forward-progress requirements.

### Rejected — notification as Promise/callback execution

```text
Atomics.notify completed
= Promise resolved
= Promise reaction executed
= user callback executed
```

These are separate semantic stages, with an additional target-Agent Job-delivery
stage possible for cross-Agent `waitAsync` resolution.

### Rejected — enqueue as immediate execution

```text
Job enqueued
= Job executing now
```

Scheduling and execution are distinct.

### Qualified — enqueue as unconditional eventual execution across termination

```text
Job enqueued
→ Job necessarily executes despite arbitrary later Agent termination
```

This is too strong. The durable evidence retains the normative scheduled-Job
invocation rule while leaving termination composition explicitly qualified.

### Rejected — termination as automatic waiter cleanup

```text
Agent terminated
→ every associated Waiter Record is automatically removed
```

No universal cleanup rule of this form was established.

### Rejected — termination as automatic waitAsync rejection

```text
Agent terminated
→ every pending waitAsync Promise is automatically rejected
```

No universal Promise rejection rule of this form was established.

### Rejected — timeout deadline as completed timeout effect

```text
Timeout deadline reached
= timeout Job executed
= waiter removed
= Promise settled
```

A timeout deadline and the later semantic effects performed by the timeout Job
are distinct stages.

## OPEN / Deferred Questions

The closure decision intentionally leaves the following questions open because
the evidence does not require a representation or universal host-lifecycle
choice now:

- concrete host outcome for Agent termination combined with a pending Job;
- concrete cleanup lifecycle for Agent termination combined with Waiter Records;
- host scheduling realization and browser-specific scheduling evidence;
- runtime event representation;
- shared-memory / memory-event representation;
- causal or evidence graph representation;
- synchronization data structures;
- async state-machine or callback-graph representation;
- Rust type and enum layout;
- crate and module placement;
- parser/static-analysis internal representation;
- public API shape; and
- serialization or wire format.

These remain future capability-design questions. An OPEN result is not permission
for the Core to invent one universal semantic outcome where the governing
standard or host contract does not provide one.

## Architecture Impact

Final architecture impact:

```text
Architecture-breaking contradiction: none found
Architecture revision required: NO
ADR 0009: Accepted unchanged
ADR 0007 / ADR 0008: unsuperseded
Browser-independent Core: preserved
Representation: OPEN
```

The post-v1.1 evidence reinforces the accepted architecture boundary:

```text
ECMAScript intrinsic semantics
!= host contract
!= browser/runtime realization
!= runtime observation
!= Core-derived interpretation
```

Browser-specific realization may supply qualified evidence, but it must not
silently become Core semantic authority.

No production Rust implementation, parser algorithm, dependency, crate topology,
public API, memory-event IR, graph structure, scheduling structure, or
serialization format is authorized merely by this closure record.

BC — CLOSED

BA–BD cross-batch adversarial audit — PASS
Post-v1.1 research wave — CLOSED / FROZEN

contradictory evidence.

Absent such a concrete trigger, additional exploratory batches should not be
created solely for completeness.

## Durable Follow-Up Rule

Future work should use this record as a research constraint and the accepted
architecture documents as normative authority.

If future evidence materially contradicts this closure state:

1. preserve the contradiction rather than forcing it into the current model;
2. identify whether it is normative, host, empirical, architecture, or
   implementation evidence;
3. reopen focused research around the concrete contradiction;
4. update or supersede this evidence record explicitly; and
5. use the repository's normal ADR / architecture process if a normative
   architecture change is required.
